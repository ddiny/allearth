# Google 로그인 후 가입 플로우 검토

## 핵심 결론

Google 로그인 사용자의 **인증용 별도 아이디 입력은 필요하지 않다.** 서버가 검증한 Google ID 토큰의 `sub`를 외부 계정 식별자로 저장하고, AllEarth 내부 회원 ID는 서버가 별도로 발급해야 한다. 이메일은 바뀔 수 있고 계정의 안정적인 고유 키가 아니므로 로그인 키나 외부 계정 연결 키로 쓰지 않는다.

현재 화면의 `아이디`가 다른 사용자에게 보이는 고유 핸들(@username)이라면 이름을 **공개 사용자명**으로 바꿔 인증 ID와 구분해야 한다. 가입 시 `공개 사용자명`과 `닉네임`을 모두 필수로 받으면 입력 부담이 커질 수 있다. 이는 제품 흐름에 대한 판단이며 사용자 실험 결과는 아니다. 권장안은 **닉네임만 필수 입력**하고, 공개 사용자명은 서버가 자동 생성해 가입 화면에서는 숨기거나 선택 입력으로 두며 이후 프로필에서 수정하게 하는 것이다. 공개 URL·멘션·검색에 고유 핸들이 꼭 필요할 때만 공개 사용자명을 유지하고, 용도와 공개 범위를 바로 설명한다.

캡처 화면은 Google 인증 성공 뒤의 **AllEarth 가입 완료 전 온보딩**이다. 이 단계에서는 아직 회원 가입이나 로그인 세션 생성을 완료했다고 표현하지 않는다.

## 이번 HTML에 반영한 범위

- A/B의 Google 버튼은 실제 Google 인증을 수행하지 않고, 테스터에서 지정한 신규·기존·취소·실패 시나리오를 재현한다.
- 신규 시나리오는 `signup.html`에서 공개 사용자명(선택), 닉네임(필수), 두 필수 체크를 확인한 뒤 `complete.html`로 이동한다. 완료 화면의 `내 지구로 가기`가 `home.html`로 이어진다.
- 기존 회원 시나리오는 가입 정보 입력을 건너뛰고 완료 화면에서 홈으로 이동하며, 취소·실패는 로그인 화면에 머무른다.
- 공개 사용자명을 비워 둔 가입 흐름은 허용한다. 실제 고유 사용자명 자동 생성·중복 검사·회원 생성은 서버 구현 대상이며 이 HTML에서는 실행하지 않는다.
- 입력값·동의·인증 토큰을 네트워크 또는 브라우저 저장소에 저장하지 않는다. 폼 값은 화면을 떠나면 유지되지 않는다.
- 완료 화면은 흐름 확인용이며, 실제 계정 생성·세션 발급의 증거가 아니다. 이메일 충돌 시 계정 연결과 임시 데이터 이관도 구현 범위 밖이다.
- 홈의 검색·이슈는 로컬 예시이며 Keep은 화면이 열린 동안의 메모리에만 유지한다. 가입 입력값·Google 계정과 연결하거나 서버에 저장하지 않는다.

## 공식 근거에서 확인되는 사실

- Google은 계정 관리의 사용자 고유 키로 `email`을 쓰지 말고 `sub`를 사용하라고 명시한다. `sub`는 Google 계정에 고유하고 재사용되지 않으며 이메일 변경에도 유지된다.
- Google의 서버 검증 가이드는 ID 토큰 검증 후 사용자를 `미가입`, `기존 로컬 계정`, `기존 Google 연동 회원`으로 구분하도록 제시한다. 기존 로컬 계정은 그 계정에 접근할 수 있음을 확인한 뒤 Google 자격증명을 연결하고, 기존 Google 연동 회원은 바로 로그인시킬 수 있다.
- 브라우저에서 받은 JWT를 그대로 신뢰해서는 안 된다. 서버에서 서명, `aud`, `iss`, `exp`를 검증해야 하며 Google 제공 라이브러리 사용이 권장된다. GIS의 POST/redirect 처리에서는 CSRF 방어도 필요하다.
- One Tap은 사용자가 취소하거나 자격증명 발급이 실패할 수 있고, 브라우저/FedCM 조건에 따라 일부 상태 알림의 가용성이 달라진다. 따라서 “버튼을 눌렀다”와 “검증 가능한 자격증명을 받았다”를 성공으로 동일 취급하면 안 된다.

공식 출처:

1. [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)
2. [Verify the Google ID token on your server side](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)
3. [Sign in with Google JavaScript API reference](https://developers.google.com/identity/gsi/web/reference/js-reference)

## 권장 계정 모델

| 데이터 | 목적 | 규칙 |
| --- | --- | --- |
| 내부 `user_id` | AllEarth 회원 PK | 서버 생성, 외부에 인증값으로 노출하지 않음 |
| `provider=google` + `provider_subject=sub` | Google 계정 연결 및 로그인 | 서버 검증 후 저장, 조합에 유일 제약 적용 |
| `email` | 연락·표시·기존 계정 후보 탐색 | 변경 가능한 속성으로 취급; 단독 자동 연결·로그인 키로 사용하지 않음 |
| 닉네임 | 앱에서 보이는 표시 이름 | 가입 시 필수로 받을 수 있음; 중복 허용 여부를 제품 정책으로 명시 |
| 공개 사용자명 | 멘션·검색·프로필 URL용 고유 핸들 | 필요할 때만 제공; 자동 생성 후 선택 수정 권장 |

`아이디 4~16자 영문 소문자·숫자·_` 규칙은 로그인 ID가 아니라 공개 사용자명 규칙으로만 사용한다. 자동 생성 시 충돌 재시도와 금칙어 예약이 필요하고, 사용자가 수정할 경우 실시간 중복 확인만 믿지 말고 가입 완료 트랜잭션에서 서버가 다시 유일성을 확인한다.

## 상태별 권장 플로우

1. **Google 자격증명 수신 전**: 취소, 팝업 닫힘, 미표시, 발급 실패는 로그인 실패/중단 상태다. 기존 로그인 화면을 유지하고 재시도와 다른 로그인 수단을 제공한다.
2. **서버 토큰 검증 실패**: 가입 화면으로 보내지 않는다. 일반적인 오류 문구와 재시도 경로를 제공하고, 검증 실패 사유나 토큰 원문은 사용자 화면·로그에 노출하지 않는다.
3. **검증 성공 + 동일 `sub` 연결 존재**: 기존 회원으로 즉시 로그인한다. 신규 가입 화면을 다시 보여 주지 않는다.
4. **검증 성공 + 동일 `sub` 없음 + 동일 이메일의 기존 계정 없음**: 짧은 수명의 서버측 온보딩 상태를 만들고 프로필/동의 화면으로 이동한다. 필수 입력과 동의를 완료한 마지막 요청에서 회원과 Google 연결을 원자적으로 생성한다.
5. **검증 성공 + 동일 `sub` 없음 + 동일 이메일의 기존 계정 있음**: 이메일만으로 자동 병합하거나 새 계정을 만들지 않는다. 기존 계정 로그인/복구 등으로 소유권을 확인한 뒤 연결할지, 다른 계정으로 계속할지 선택하게 한다. 이미 다른 Google `sub`가 연결된 경우에는 별도 충돌 안내와 계정 복구 경로가 필요하다.
6. **온보딩 중 뒤로 가기·탭 닫기·만료**: 완료 회원으로 만들지 않는다. 재진입 시 검증된 Google 계정을 기준으로 안전하게 이어서 하거나 만료 후 다시 인증한다.
7. **가입 완료 동시 요청/중복 제출**: `(provider, sub)` 및 공개 사용자명 유일 제약과 멱등 처리를 서버에서 적용해 중복 회원 생성을 막는다.

계정 연결은 보안 영향이 큰 별도 행위다. 프런트에서 이메일 일치만 보고 결정하지 말고, 서버 정책과 기존 계정 소유권 확인을 거쳐야 한다. Google 문서도 기존 로컬 계정에는 암호 입력 등으로 접근 권한을 확인한 뒤 연결하는 흐름을 예시로 든다.

## 화면 문구와 입력 구조 권장안

- 상단 상태: `Google 계정 인증 완료` 또는 `프로필 설정 · 가입 2/2`
- 제목: `지구에서 쓸 이름을 정해주세요`
- 계정 확인: 마스킹한 Google 이메일과 `계정 변경` 제공
- 필수 입력: `닉네임 (2~12자)` 하나
- 선택 입력이 꼭 필요한 경우: `공개 사용자명 (선택)`과 `@사용자명으로 검색·멘션·프로필 주소에 표시됩니다` 설명. 기본값은 서버 자동 생성
- 동의: 전체 동의는 하위 항목을 조작하는 편의 기능으로 두고 필수 동의와 선택 동의를 시각적으로 구분. 가입 버튼 활성화는 필수 입력의 서버 규칙 충족과 필수 동의 선택에만 연동
- 완료 버튼: 비활성 상태만 보여 주지 말고, 누락 항목을 인라인으로 설명. 제출 중 중복 클릭을 막고 서버 오류·사용자명 충돌·온보딩 만료를 각각 복구 가능한 상태로 처리
- 성공 시점: 서버가 회원 생성, Google `sub` 연결, 동의 기록, 세션 발급을 성공시킨 뒤에만 `가입 완료`로 표시

현재 표시된 개인정보 수집·이용 및 연령 동의 항목의 법적 충분성은 실제 약관 원문, 수집 항목·목적·보유 기간, 서비스 대상과 적용 법률을 확인하지 않고 판단할 수 없다. 이 문서는 인증·계정·UX 플로우만 검토한다.

## 프로덕션 체크리스트

- HTTPS로 받은 Google credential을 백엔드에 전달하고 Google 공식 라이브러리 또는 검증된 JWT 라이브러리로 서명과 `aud`·`iss`·`exp`를 검증한다.
- GIS POST/redirect 흐름은 CSRF 토큰을 검증하고, OIDC 요청 흐름에 해당하면 `state` 및 `nonce`를 설계에 맞게 검증한다.
- 검증된 `sub`만 외부 계정 키로 저장하고 `(provider, sub)` 유일 제약을 둔다. 이메일과 화면에서 디코딩한 JWT만으로 회원을 생성하지 않는다.
- 신규 회원 생성, 외부 계정 연결, 동의 버전/시각 기록, 세션 발급의 경계를 서버 트랜잭션과 멱등 키로 보호한다.
- 기존 회원, 신규 회원, 동일 이메일 충돌, 다른 `sub` 연결 충돌, 사용자 취소, 토큰 만료·위조·잘못된 `aud`, 온보딩 이탈, 공개 사용자명 경합을 통합 테스트한다.
- 토큰 원문과 불필요한 Google 프로필 정보는 저장하지 말고, 필요한 데이터·보유 기간·삭제 및 연결 해제 정책은 별도 제품/법무 검토로 확정한다.
